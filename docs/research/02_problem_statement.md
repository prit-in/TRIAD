# 2. Problem Statement

A modern analytics pipeline is not one program. For the churn case studied here it is ingestion
and profiling in Python, cleaning and feature construction as Spark jobs, a hand-off to Python
for model training and calibration, a registry, scoring, monitoring, and a report - five or more
components in three languages, run on a schedule, against data that change. Fig. 3 groups the
difficulties this creates into five families, and Table 2 divides them into the seven specific
challenges this work takes on, stating for each what current practice does, what is missing, and
what this work does about it.

**Fig. 3. Challenges in Modern Data Science Platforms.** *(figures/fig03_challenges.drawio)*

**Workflow complexity.** Every boundary between languages and engines is a place where an
assumption is lost: a date becomes a string, a partition column changes type, a stage reads a
folder that another run is overwriting. Studies of production machine learning find such
integration problems, rather than modelling problems, dominate the effort of deployment
[@paleyes2022deploying] [@lwakatare2020industrial].

**Code maintenance.** Hand-written transformation jobs accumulate special cases, and code
generated by an LLM can be correct-looking and wrong, or insecure [@pearce2022asleep]
[@tihanyi2024secure]. A generator without constraints moves the maintenance problem rather than
removing it.

**Scalability.** Whether a step should run in a single Python process or on a Spark cluster
depends on data size, and the choice is usually made once, by hand, and never revisited. Tuning
Spark itself is a research field of its own [@herodotou2020tuning].

**Heterogeneous environments.** Python, the Java virtual machine, Scala, Spark, and their
libraries each have versions, and a pipeline that works on one machine fails on another for
reasons unrelated to its logic.

**Analytics automation without accountability.** Automated machine learning (AutoML) can choose
and tune a model [@he2021automl] [@karmaker2021automl], but choosing a model is not the same as
deciding that it is fit to use. Calibration, fairness across customer segments, comparison with
the model already in production, leakage, and the approval to deploy are decisions with
consequences, and a platform that automates them without recording why has removed the person
who would have been accountable [@raji2020accountability].

**Table 2. Research Challenges and Gaps**

| Challenge | Current practice | Gap | This work | Evaluated in |
| --- | --- | --- | --- | --- |
| Multi-language workflows | Hand-offs between notebooks, scripts, and scheduled jobs | No single record of what ran, on which data | One run record: every stage, its decision, its exact input versions | Sections 11, 17; replay test |
| Generated and hand-written code | Free-form code, reviewed by eye | Nothing bounds what generated code may change | Templates with named slots and nine validation gates | Section 7; EXP-8 |
| Scale decisions | Engine chosen once, by hand | Choice not revisited, not recorded | Ordered routing rules, each match recorded with its evidence | Section 9; EXP-1 to EXP-3 |
| Environment drift | Per-machine installs | Results not reproducible across machines | One pinned toolchain image; versions read from the image | Section 13 |
| Point-in-time correctness | Features computed on full history | Leakage inflates measured accuracy | Snapshot expansion at each cutoff; hygiene and leakage checks | Section 8; EXP-9 |
| Automated model acceptance | AutoML maximizes one metric | Calibration, segments, and champion comparison not enforced | Acceptance policy AP-1 to AP-8; approval with separation of duties | Sections 10, 12; EXP-5, EXP-10 |
| Silent degradation | Monitoring detached from retraining | Drift noticed late, retraining ad hoc | Drift reports and nine retraining rules on a schedule | Section 11; EXP-7 |

Stated precisely, the problem this report addresses is the following. Given a set of versioned
source tables for a retail business, produce churn probabilities for its customers such that
(i) every transformation is executed by code that passed stated checks, in an isolated
environment; (ii) every result can be traced to, and reproduced from, the exact input versions
and code that produced it; (iii) a model is used only if it meets a written acceptance policy and
a person other than its requester approves it; and (iv) the engineering work between those
decision points is automated by agents. The question is how much of a data science pipeline can
be automated under those four constraints, and at what cost.
