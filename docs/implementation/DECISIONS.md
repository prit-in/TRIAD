# Implementation decisions

Small decisions taken while building, where the PRD left a detail open or where measurement
showed the literal reading would misfire. Anything architectural gets a full ADR in
`docs/adr/` instead.

| ID | Decision | Why | PRD anchor |
| --- | --- | --- | --- |
| DEC-01 | Calibration-sensitive acceptance rules (AP-4 Brier skill, AP-5 calibration error) are judged **after** stage C calibration, not during stage A screening. Screening keeps AP-3, AP-7 and the leakage alarm. | PRD 17.7 states that class weighting distorts probabilities, and AP-5 is defined as "at most 0.05 **after calibration**". Measured on the fixture: every weighted candidate had a negative Brier skill before calibration, so screening on it rejected the whole shortlist and escalated a healthy run. | 17.6, 17.7, 18.2 stage C, 18.4 |
| DEC-02 | A segment counts towards the AP-6 recall gap only with at least 50 rows **and 30 positives**; otherwise it is marked `insufficient_data`. | UC-10's exception flow already marks thin segments. Recall from ~12 churners is sampling noise; without the positives rule the gap was 0.34 on a fixture whose segments were statistically indistinguishable. | UC-10, AP-6 |
| DEC-03 | The MISCALIBRATED remedy chain is isotonic -> sigmoid -> refit without class weighting, each attempt recorded in the decision evidence. | This is PRD 19.4's remedy row implemented literally ("Recalibrate (isotonic, then sigmoid)" then "Reduce class weighting"). | 19.4 |
| DEC-04 | Thin JARs: `sbt core/package jobs/package`, and the Execution Agent submits with `--jars <core>`. No assembly plugin. | Spark stays `provided` (FR-041) and no extra build plugin has to be downloaded or trusted. Found during the Phase-1 smoke test, where `jobs/package` alone produced `NoClassDefFoundError: triad/core/Inputs`. | FR-041, 36.3 |
| DEC-05 | Every Python-side Parquet write goes through `triad_core.parquet_io.write_parquet`, which coerces timestamps to microseconds. | pandas/PyArrow default to nanoseconds and Spark 4 refuses to read them (`PARQUET_TYPE_ILLEGAL`). PRD 13.5 already pins `TIMESTAMP_MICROS` on the Spark side; this closes the other half. | 13.5, 23.2 |
| DEC-06 | `sha256_dir` excludes `_SUCCESS`, `_manifest.json` and `.crc` sidecars. | The manifest contains the content hash, so including it would make the hash depend on itself and `verify()` could never pass. | 14.2, NFR-REP-02 |
| DEC-07 | A shared `triad_core/` package holds config, models, storage, audit, policy, contracts and errors; `dataeng/` holds M02-M04 services. | PRD 38's tree has no shared layer, so backend, agents and python_ml would each need their own copy of the state handling. Module boundaries from PRD 37 are preserved. | 37, 38 |
| DEC-08 | Profiling always reports nulls in an `identifier` column, even below the 20% warn rate. | Those rows cannot be joined to a customer and are quarantined as `NO_CUSTOMER_KEY` in P3, so the profile must surface them. The PRD's own example calls out "3% of lines lack a customer ID" as a finding. | UC-02, UC-03, FR-010 |
| DEC-09 | Gate 4 runs `sbt core/package jobs/package`, not `jobs/compile`. | Gates 6 and 9 submit JARs. Compiling alone leaves the generated class in `target/classes`, so `spark-submit` loaded a JAR packaged before the artifact existed and failed with `Failed to load class triad.jobs.generated.CleanJob_<hash>`. `package` depends on `compile`, so compile errors surface exactly as before. | 21.1 gates 4/6/9, DEC-04 |
| DEC-10 | `JobConfig.dataEnd` has no default: a job that reads it without `--param=data_end` raises `ContractViolation`. | It used to default to the last cutoff, and a label matures only when `snapshot_date + horizon <= data_end`, so the default silently made every snapshot immature and the label job wrote zero rows. There is no safe default for "where the data ends". | 17.1 maturity rule, FR-030 |
| DEC-11 | `read_parquet` restores partition columns to the type the writer's manifest declares, and never returns a partition column as a Categorical. | A Hive path holds `snapshot_date=2026-04-01` as a directory name, so a partitioned date read back as a string while the same column from an unpartitioned set read back as `datetime.date`. The feature/label join then matched nothing while both row counts looked correct. The manifest carries the real schema, so nothing is guessed. | 13.5, 14.2 |
| DEC-12 | The cleaning stage is held against the `cleaning.execute` limits (`max_rows_affected_pct`, `quarantine_required`) after the job runs and **before** its output is committed, using the job's own row accounting. | The policy engine existed and was tested, but no pipeline stage called it, so a governed action was running ungoverned. Gating the commit rather than the sandbox run means the decision is made on measured rows, not an estimate. | 30, 51, FR-023 |
| DEC-13 | Templates are refused at parse time when they carry an import nothing uses, and `load_templates` re-raises a real template defect instead of skipping the file. | `-Wconf:src=.*generated.*:error` makes warnings fatal inside `triad.jobs.generated` only, so a template can compile in place and fail gate 4 on every generated copy - three sbt attempts and two minutes into a run. Skipping the file instead turned a clear message into a `KeyError` in the stage that needed it. | 21.2, FR-038 |
| DEC-14 | A churn run is two phases - `churn.prepare` and `churn.publish` - either side of the approval gate, and the second rebuilds everything it needs from a `run_state.json` written by the first. | A run genuinely pauses for a person, possibly for days, so nothing may be carried across in memory. Writing the state down is also what lets the worker be restarted, or crash, between the two halves without losing the run, and it is the same "data moves by reference" rule the rest of the platform follows. | 39, 14.2, DD-02 |
| DEC-15 | Cutoffs are derived from the cleaned data's own first and last dates, not from a `--months` parameter. | The demo assumed the data started on its configured start date; the first customer order is actually a few days later, so the assumed first cutoff had less than the 365 days of history its features claim. Deriving gives 2025-02-01 where assuming gave 2025-01-01. `JobConfig.dataEnd` already refuses to guess (DEC-10); this closes the same gap at the other end. | 17.1, 17.2 |
| DEC-16 | `POST /pipelines/run` resolves a dataset *name* to its latest version URI at request time, and refuses an unknown or version-less dataset with 422. | The alternative is a worker failure ten minutes later with the same cause and a worse message. It also means the run record stores the exact version it ran on rather than a name that may since have moved. | 25.2, 24.1 |
| DEC-17 | The audit trail is one hash chain per run, plus one for entries belonging to no run, each appended under a transaction-scoped PostgreSQL advisory lock. | A single global chain forked in practice: appending means reading the head and inserting, and two writers did both before either committed. `verify_chain` then reported tampering that had not happened, which is the worst failure a tamper-evidence mechanism has. Serialising one global chain would fix the fork but make every login wait behind the longest open pipeline transaction, which is minutes. Per-run chains confine the lock to the chain being appended to. Residual limit, stated rather than hidden: removing an entire run's chain is not detected by chain verification alone. | 24.4, FR-078, TC-078 |
| DEC-18 | One run of a given pipeline at a time, enforced by an advisory lock in `churn.prepare` and a 409 from `POST /pipelines/run`. | Runs share `clean/`, `features/` and `labels/`, and committing supersedes what is there, so a second concurrent run replaced the first one's inputs mid-flight - observed as a feature job failing on data that had changed underneath it. Lifting the restriction means versioning those outputs per run, which is a storage-layout change rather than a lock. | 14.2, 25.2 |
| DEC-19 | Selection scores the deployed champion on the same test cutoff and passes those scores to the acceptance policy. | AP-8 is defined as a comparison against the champion. Without the champion's scores the rule had nothing to compare against, so every run behaved as though it were the first and the requirement that a challenger beat what is deployed never applied. A champion that exists but cannot be scored escalates, because "could not compare" is not the same as "nothing to compare with". | 17.6 AP-8, 18.4 |
| DEC-20 | The error taxonomy gains two classes the PRD's playbook has no row for: `DEPENDENCY_RESOLUTION` (resubmit once, never regenerate code) and `RESOURCE_CONFIG_INVALID` (no automatic remedy, no retry, escalate naming the setting). The compile-error pattern now requires a file path and line number straight after `[error]`, and gate 4 claims a compile error only when the compiler reported one. | EXP-6 measured both failures going wrong. A coursier download failure was classified `SCALA_COMPILE_ERROR` - the old pattern matched any `[error]`-prefixed stack frame in a `.scala` file, and gate 4 set that class on every non-zero sbt exit as a hint that skips pattern matching - so correct code would have been regenerated. Spark refusing to start with `[INVALID_DRIVER_MEMORY]` was `UNKNOWN`. Driver memory is deliberately not on the `spark.config_change` allowlist, so the agent is not permitted to raise it; widening the policy to make EXP-6's hypothesis hold would have been changing the expectation to obtain the result, so the setting is named in the escalation instead. | 20.1, 20.2, 21.1 gate 4, LR-10 |
| DEC-21 | `country` and `acquisition_channel`, in PRD 16.1's Profile group, are joined for evaluation and are not model inputs; `configs/feature_catalog.yaml` marks them `evaluation_only`. `loyalty_tier_at_cutoff` and `marketing_opt_in_at_cutoff` are marked `unavailable`. | AP-6 asks whether a model built from behaviour treats country groups differently; a model given `country` as an input answers a different question, and the check stops meaning anything. Keeping the columns out was also needed in practice: joining them for AP-6 once turned them into features by accident, because the training calls derived their feature list from the frame, and every family's validation PR-AUC moved. The limit, stated: leaving an attribute out does not remove its proxies, which is why AP-6 measures outcomes instead of relying on the omission. The two `_at_cutoff` attributes need a dated history the customers table does not have, and its current value would leak a later state into earlier cutoffs (ASM-11). | 16.1, 17.6 AP-6, ASM-11, FR-025 |
| DEC-22 | A retraining attempt that fails still counts against the cooldown: the scheduler starts at most one retrain of a pipeline per cooldown window, whatever became of it. | PRD 19.3 measures the cooldown from training, and a retrain that keeps the champion does not move that, so without a guard on attempts a fired trigger would start a run on every five-minute tick. Counting only successful attempts would turn a deterministic failure into a run every five minutes. Each skipped tick is audited as `retraining.not_started` with the run that used the window, and a person can still start a run at any time. (Retraining on the newest window, and with a fresh budget, is PRD 19.3 as written, not a decision: copying the source run's inputs and budget was a defect, found live on 2026-10-03.) | 19.1, 19.3, FR-074 |
| DEC-23 | The orchestrator's memory limit is 2600M (was 1600M), with `SBT_OPTS=-Xmx800m` and the forked test JVM's heap set by `TRIAD_TEST_HEAP=700m`. MLflow runs with `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false`. | Gate 5 runs sbt and a forked ScalaTest JVM at once beside the worker, and their default heaps (1 GB and 1500m) alone exceeded the old limit. MLflow 3.x starts a job runner and seven huey consumers of about 200 MB each by default, for server-side GenAI jobs TRIAD never submits; measured at 1.15 GiB of its 1.17 GiB limit with them, 417 MiB without. The core profile still fits ADR-0002's 5.27 GB VM. | 21.1 gate 5, ADR-0002 |
| DEC-24 | **Deviation from CR-08, recorded late.** A run's control loop is a PostgreSQL state machine and task queue (`agents/graph/queue.py`, `agents/worker.py`, `churn.prepare`/`churn.publish`), not a LangGraph graph. LangGraph 1.1.10 and its PostgreSQL checkpointer are installed and pass the Phase-1 smoke test (interrupt, then resume through a second saver), but no runtime code imports them. | The PRD chose LangGraph for checkpointing after every node, a human pause that survives restarts, and resume. Each is met another way, with evidence: every state transition is committed with its audit entry as it happens (FR-073); the approval pause is the `APPROVAL_REQUIRED` state plus `run_state.json`, which the publish phase rebuilds from with no process alive in between (DEC-14); a crashed worker's task is re-queued when its lease expires and resumed (AT-11, observed on run-2026-10-03-002); budgets and attempt counters live on the run row. What is not delivered: an explicit graph definition and LangGraph's tracing. This was not recorded when the runtime was built, and the audit of 04-10-2026 found the gap between CR-08 and the code. | CR-08, 10.3, 12.x, 37 M07 |
| DEC-25 | The resource profiles' process limits are 512 / 1 024 / 2 048 (small / medium / large), double PRD 22.4's illustrative 256 / 512 / 1 024, and the full execution of a generated job runs under `medium` while its gate-6 dry run keeps `small`. | Every thread of the Spark driver counts against the container's `pids` limit. Measured through the cgroup's `pids.peak`: the feature job peaks at 284 threads on its 1 000-row dry run and 292 on the full 800-customer job. At 256 it failed with "unable to create native thread" - or, worse, ran into the 600 s timeout first, because a JVM whose thread creation keeps failing retries rather than stops (603 s against 60 s with headroom). The limit still does what it is for - a fork bomb stops at 512. PRD 22.4 assigns `small` to "dry runs, tests" and `medium` to "Spark client"; until now every job ran as `small`, whose 10-minute timeout a full job at a larger tier would reach. The first diagnosis of this failure was UNKNOWN, because the error kept only a trace's last 4 000 characters; exception lines are now kept, and thread exhaustion is `RESOURCE_CONFIG_INVALID`. | 22.2, 22.4 (EX), ADR-0004 |
| DEC-26 | AP-6's recall gap is computed within each segmentation - countries against countries, tenure bands against tenure bands - and the largest of those gaps is judged. The segmentations are `country`, `loyalty_tier`, `acquisition_channel`, and a `tenure_band` derived from `tenure_days` for evaluation only. The acceptance decision records every segment's rows, positives, and recall. | The gap was the largest minus the smallest recall over every segment of every attribute together, so a country's recall was compared with an acquisition channel's: overlapping groups from different partitions, with each added attribute widening the gap. run-2026-10-04-004 escalated on a "gap" of 0.160 computed that way, and its decision record held that one number and nothing a reviewer could judge it by. PRD AP-6 names "country group, tenure band", and tenure band was not checked at all. A segment still needs 50 rows and 30 positives to count (DEC-02). | 17.6 AP-6, FR-060, UC-10 |
| DEC-27 | A promotion despite a failed check is possible only for a candidate that failed a calibration rule (AP-5) or a segment rule (AP-6) and would otherwise have been proposed - it beats the champion with confidence (AP-8), or there is no champion. It needs one approval per role in `approvers_all_of` (ML Engineer and Admin), each decided by that role only, by a different person, neither the requester nor whoever started the run, and a written justification. The segment-aware threshold review of PRD 19.4 is recorded with the AP-6 escalation as analysis and never applied. | PRD section 30 defines the action and `governance.yaml` defined it too; nothing requested it, so an escalated run had no governed way forward but a new run. Restricting it to AP-5 and AP-6 keeps the rules that guard against a wrong model rather than a noisy measurement - leakage, the PR-AUC and ROC-AUC floors, cost - out of reach of an override, and requiring AP-8 means nobody is asked to override for a model that would not have won. The review is analysis because an operating threshold per group is a policy decision, and for an attribute such as country a contested one; the measurements behind it (`experiments/policy_floors/segment_gap_noise_floor.json`, run-2026-10-04-006's tenure band) are what an approver needs to tell a noisy check from a real disparity. | 19.4, 30, UC-17, FR-075 |
| DEC-28 | The run state machine is enforced: `queue.set_state` checks every move against `ALLOWED_TRANSITIONS`, and the table lists the lifecycle runs actually follow - read from the transitions recorded in `audit_logs` for all 96 runs - plus the PRD's own states. Staying in a state is not a move. | PRD 12.2-12.4 define the machine and its guards. `check_transition` existed and had no caller, so any move was accepted, and the table had drifted: it refused PLANNED -> FEATURES_READY, which every successful run makes, because code generation, validation and execution are recorded per stage in `code_artifacts` and `executions` rather than as run states. Enforcing the old table would have failed every run; enforcing nothing let a bug such as a double SELECTED advance (recorded 14 times) pass unseen. | 12.2, 12.3, 12.4, FR-073 |
| DEC-29 | Per-stage Spark metrics come from a `SparkListener` (`triad.core.StageMetricsListener`) registered by `TriadJob` before its first read, and `TriadJob` now stops Spark *before* writing its report. The stages travel in the job report as `spark_stages` and are stored on the execution under one `spark` key, beside the job's own metrics. | FR-036 asks for "Spark's monitoring API". The REST endpoint is unreachable by design - the sandbox has no network and the UI is off (ADR-0004) - and event logs would mean a log directory per job and a parser for a format Spark does not promise to keep stable; the listener API is the same data, in-process. Listener events are delivered asynchronously, and `SparkContext.stop()` is what drains the bus, so a report written before stopping could miss the last stage. The job's measured `duration_ms` is still taken before the stop, as it was. | FR-036, 21.2, ADR-0004 |
| DEC-30 | FR-022's anomaly checks run in the profiler. A business-rule breach - the rules cleaning quarantines on - is a `warning`; a volume anomaly (a day's row count beyond a modified z-score of 3.5, the first and last days excluded) and a distribution shift (PSI of at least 0.10 against the previous version) are `info`. PSI is computed on the previous version's own quantile bins, with each version's bin shares counted rather than read off the quantile levels. | A breach is a defect in the data and the quality score already counts validity warnings. A volume anomaly or a shift is a fact about the population, not a defect: scoring it would lower Q for data that is merely different, and acting on drift is the drift monitor's job (FR-081). Counting shares matters because of ties - most quantities are 1, so far more than 25% of rows sit at or below the 25th percentile - and the version-comparison "PSI" FR-015 already reports is a relative quantile shift, which is why this one is computed separately and named for what it is. | FR-022, FR-015, FR-081, Eq. 7 |
| DEC-31 | The configuration optimisation loop tunes one setting, `spark.sql.shuffle.partitions`, within 2 to 64. OPT-1 doubles it when the previous run of the same pipeline's stage spilled; OPT-2 halves it when that run's reduce stages had a median task under 50 ms. The change applies to the next run's stage, never mid-run, and is recorded twice: the change with the measurements behind it, and after execution the before-and-after comparison, whose verdict reads a wall-clock difference inside +/-10% as no difference. A replay uses the replayed run's value unchanged. | PRD 30 makes Spark setting changes L3 with "before-and-after metrics" as the evidence, and LR-10 limits the agent to allowlisted settings. Shuffle partitions is the one every job takes as an argument, so the change needs no new plumbing and cannot reach a setting the policy does not list. Keying on pipeline and stage keeps one experiment's trials from steering another's. One run each side is all a before-and-after has, so the record says only whether the clock moved beyond noise, not that the setting caused it. | FR-037, 30, LR-10 |
| DEC-32 | FR-072's PDF is printed by the browser from the document the page shows, in a second sandboxed frame with `allow-scripts allow-modals` and no `allow-same-origin`; the frame that displays the report keeps no permissions at all. | "Exports match the on-screen report" is satisfied by construction when both are the same document; a server-side renderer would be a second report to keep in step and a large dependency (a headless browser) in the API image. Printing needs a script, so the print happens in a frame of its own whose opaque origin cannot reach the page, its token or the API. | FR-072 |

EXP-3 reported its own dependent measures as absent. EXP-5's 324-row validation split sat inside AP-5's measured noise floor (`calibration_noise_floor.py`: a perfectly calibrated model fails 40-46% of the time at that size, about 0% at 1 300 rows), and its escalated conditions recorded no PR-AUC although, since DEC-27, the escalated candidate is scored on the test cutoff exactly once. None of these reads a result of the experiment it changes. | 33, 32.1, DEC-27 |

EXP-1 counts configuration P as having run end to end when it reached selection, records the escalated candidate's own test figures (scored once on the test cutoff since DEC-27) with the policy's verdict beside them, and runs the baselines on P's split as before. | EXP-1's re-run on 08-10-2026 failed outright: P escalated MISCALIBRATED on a validation split inside AP-5's measured noise floor, the escalation returned nothing but the selection, and the experiment, having no split to give the baselines, stopped. | DEC-35 | Memory limits are limits on memory plus swap: sandbox jobs get `memswap_limit` equal to `mem_limit`, and the dev container `memswap_limit: 3000M`. ST-07's test now asserts `memory.swap.max = 0` inside a job. | DEC-36 | Cleaning conforms the columns the transactions contract declares numeric (`price`, `discount`, `quantity`) before any rule reads them: a leading or trailing three-letter currency code is removed only where it agrees with the row's own `currency` column, the rest goes through `try_cast` to the declared type, and a value that still does not parse is quarantined as `INVALID_CAST_<COLUMN>` with its original text kept beside it. A column that is already numeric is untouched. | EXP-4 found the hypothesis "prices are fixed by try_cast and quarantine" unmet: with prices as text ("INR 871.59") the rule `price > 0` made ANSI mode cast text to a number and fail the job; the repair loop diagnosed `INVALID_CAST_ANSI` with the right remedy, had no way to apply it in template-only mode, and the circuit breaker escalated. | DEC-40 | A cleaning plan over its `cleaning.execute` limit files a `destructive_cleaning` approval (impact by rule, sample quarantined rows) once per run and stage, and the run pauses in `APPROVAL_REQUIRED` with its output uncommitted and its quarantine kept; the phase succeeds, so the task is not retried into the same request. | DEC-41 | An out-of-memory in a sandboxed job is classified and remedied as PRD 20.2 reads, within the policy: a task's heap exhaustion in local mode ("Lost task ... executor driver ...
